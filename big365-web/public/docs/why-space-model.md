# 为什么不是普通表？—— Space 预计算模型的设计动机

如果你第一次看到 big365，很可能会产生一个疑问：

> "不就是个多维数据表吗？我直接建一张 MySQL 表，写几条 SQL 就行了，为什么要搞这么复杂的 Space 模型？"

这是一个非常好的问题。本文用具体的例子来说明：**普通表做多维分析会遇到什么麻烦，Space 模型又是如何解决这些麻烦的。**

读完本文，你会理解 big365 的设计取舍，以及它最适合用来解决哪类问题。

---

## 1. 普通表的困境

假设你在做**日志监控**。你关心 3 个分析维度：
- **应用**（app）：3 个应用（order-svc、user-svc、pay-svc）
- **接口**（endpoint）：5 个接口（/api/order、/api/user、/api/pay 等）
- **状态码**（statusCode）：3 种状态（200、404、500）

每天写入一条数据："应用 1 的接口 2 返回了 200，请求量 100"，按传统思维，你建一张最直观的**明细表**：

```sql
CREATE TABLE log_records (
    id       BIGINT AUTO_INCREMENT PRIMARY KEY,
    app      INT NOT NULL,
    endpoint INT NOT NULL,
    status   INT NOT NULL,
    date     DATE NOT NULL,
    value    BIGINT NOT NULL
);
```

写入很简单：

```sql
INSERT INTO log_records (app, endpoint, status, date, value)
VALUES (1, 2, 200, '2026-06-10', 100);
```

### 1.1 查询的"爆炸"

但问题出在**查询**上。你的老板想看看：

> "昨天 order-svc（app=1）所有接口的请求总量是多少？"

用 SQL 写：

```sql
SELECT SUM(value) FROM log_records
WHERE app = 1 AND date = '2026-06-10';
```

假设有 1000 条明细记录，这个查询需要**扫描 1000 行**，然后 **SUM 聚合**。数据量再大一点——10 万条？100 万条？扫描成本直线上升。AND 条件少了，扫描行数多；AND 条件多了，组合数指数增长。

### 1.2 索引救不了你

你加个索引：

```sql
CREATE INDEX idx_query ON log_records(app, endpoint, status, date);
```

看起来加速了，但真实场景是：
- 老板先问"app=1 的全部汇总" → 一次查询 
- 又想"app=1 且 status=200 的汇总" → 又一次查询
- 第三天想看"所有 app 的 404 比例" → **跨维度**组合查询

索引可以加速，但不能消除聚合计算。每次查询都要走一遍 `SUM`，而且复杂的组合查询往往**不走索引**。MySQL 最终会退化到全表扫描。

### 1.3 真正的麻烦：组合爆炸

上面的例子只有 3 个维度。实际业务中，5 个维度非常常见。来看看 3 维和 5 维的区别：

| 维度数 | 维度取值 | 可能的查询组合数 |
|--------|----------|----------------|
| 3 | app(3) × endpoint(5) × status(3) | **2³ = 8** 种（含全部/单维/两维/三维的交叉上卷）|
| 5 | app(3) × endpoint(5) × status(3) × env(2) × region(3) | **2⁵ = 32** 种 |

8 种查询组合你还能硬扛——预建 8 个索引或者写 8 条不同 SQL。但 32 种呢？再往上呢？**这是一条死路。**

如果你还想要"最近 7 天的汇总"——那就不是在查一张表了，而是在每张表上反复执行聚合查询。**复杂度 = 天数 × 查询组合数**。

## 2. Space 模型的解决思路

big365 的 Space 模型采用了一种**反直觉**的策略：

> **写入时多做一些计算，查询时就可以零聚合直接返回结果。**

这个策略有三大支柱：

### 2.1 支柱一：0=ALL 哨兵

Space 模型用坐标值 **0** 代表 **"ALL"（全部，即上卷）**。

举例：当有 app、endpoint、status 三个维度时：

| 坐标值 | 含义 |
|--------|------|
| `(0, 0, 0)` | **所有 app、所有 endpoint、所有 status ——  全局总计** |
| `(1, 0, 0)` | app=1 在**所有** endpoint 和**所有** status 上的聚合 |
| `(1, 2, 0)` | app=1、endpoint=2 在**所有** status 上的聚合 |
| `(1, 2, 200)` | app=1、endpoint=2、status=200 的**叶子级精确值** |

每个维度只有两个状态：要么是具体值（1, 2, 3...），要么是 ALL（0）。维度越多，**N 个 0/非0 的组合数 = 2^N**，恰好覆盖了所有可能的"上卷"查询。

### 2.2 支柱二：级联写入

当一个用户**写入一条数据**时，比如：

```
坐标: (app=1, endpoint=2, status=200), 日期: 20260610, 指标值: 100
```

Space 模型不会只写 1 行，而是**自动生成 2³ = 8 行**，把这条数据在所有上卷级别上的贡献提前算好：

```
┌─────┬──────────┬──────┬──────────┬──────┐
│ app │ endpoint │ status │ 20260610 │ 说明                            │
├─────┼──────────┼──────┼──────────┼─────────────────────────────────┤
│  1  │    2     │  200  │   100    │ 叶子级: 最详细                   │
│  1  │    2     │   0   │   100    │ app=1, endpoint=2, 全部 status   │
│  1  │    0     │  200  │   100    │ app=1, status=200, 全部 endpoint │
│  1  │    0     │   0   │   100    │ app=1 的全部                     │
│  0  │    2     │  200  │   100    │ endpoint=2, status=200, 全部 app  │
│  0  │    2     │   0   │   100    │ endpoint=2 的全部                │
│  0  │    0     │  200  │   100    │ status=200 的全部                │
│  0  │    0     │   0   │   100    │ 全局总计                         │
└─────┴──────────┴──────┴──────────┴─────────────────────────────────┘
```

如果有后续写入（同一坐标 + 同一日期），系统会在**原有行上累加**（INSERT ... ON DUPLICATE KEY UPDATE），8 行会同时更新。

### 2.3 支柱三：零聚合 O(1) 查询

因为所有聚合结果已经在写入时算好并存入了对应的行中，**查询变得极其简单**：

```bash
# 老板想看："app=1 所有接口的总量"？
# → 坐标: (app=1, endpoint=0, status=0)
# → 定位到唯一一行 → 直接读值 → 完成！
# SQL: SELECT `20260610` FROM space_t WHERE app=1 AND endpoint=0 AND status=0
# 扫描: 1 行。时间复杂度: O(1)。

# 老板想看："app=1 接口 2 的 200 状态码精确值"？
# → 坐标: (app=1, endpoint=2, status=200)
# → SQL: SELECT `20260610` FROM space_t WHERE app=1 AND endpoint=2 AND status=200
# 扫描: 1 行。O(1)。

# 老板想看全局总计？
# → 坐标: (app=0, endpoint=0, status=0)
# 扫描: 1 行。O(1)。
```

**无论数据量多大，查询永远只扫描 1 行。**

## 3. 具体对比：普通表 vs Space 模型

下面用同一个业务场景——3 维度日志分析，写入 1000 条明细数据——来对比两种方案：

### 3.1 存储行数

| 方案 | 写入 1 条产生的行数 | 写 1000 条后的总行数 |
|------|-------------------|---------------------|
| 普通表 | 1 行 | **1,000 行** |
| Space 模型（3 维） | 2³ = 8 行 | **最多 8 × 所有唯一坐标组合** ≈ 2,160 行 (假设 270 个唯一组合) |
| Space 模型（5 维） | 2⁵ = 32 行 | **最多 32 × 唯一组合** ≈ 14,400 行 |

> Space 模型存储更多的行，但上限是 `(leaf_max₁+1) × (leaf_max₂+1) × ... × 日期数`，不会无限增长。

### 3.2 查询成本

查询："app=1 的所有数据汇总"（数据量：100,000 条明细）

| 方案 | SQL | 扫描行数 | 响应用时（估算） |
|------|-----|---------|-----------------|
| 普通表 | `SELECT SUM(value) FROM log_records WHERE app=1 AND date=`... | ~33,000 行 + 聚合计算 | 200~500ms（随数据量线性增长）|
| Space 模型 | `SELECT \`datecol\` FROM space_t WHERE app=1 AND endpoint=0 AND status=0 AND ...` | **1 行** | **<1ms**（固定，不随数据量增长）|

### 3.3 多日区间查询

查询："app=1 最近 30 天的**每日**请求量"

| 方案 | 做法 | 复杂度 |
|------|------|--------|
| 普通表 | 30 次 `SUM` + `GROUP BY date`，或 1 次全表扫描 + 应用层聚合 | 高，随天数线性增长 |
| Space 模型 | 30 次单行查询（每日坐标相同），应用层简单 SUM | O(天数)，但每天都是 1 行扫描 |

### 3.4 一个直观的数字对比

| 场景 | 普通表 | Space 模型 |
|------|--------|-----------|
| 写入 1 条 | 1 行 INSERT | 2^d 行 INSERT/UPDATE |
| 查询"app=1 总量" | SUM 扫描 ~33,000 行 | **O(1)** 定位 1 行 |
| 查询"全局总计" | SUM 扫描全部 100,000 行 | **O(1)** 定位 1 行 |
| 多维组合查询（如"app=1 AND statusCode=200 总量"） | 全表扫描或索引跳跃 | **O(1)** 定位 1 行 |
| 5 维查询"app=1, endpoint=2, status=200, env=1 总量" | 复杂的多条件聚合 | **O(1)** 定位 1 行 |

## 4. Space 模型的代价与适用场景

没有完美的方案，Space 模型也有它的代价：

### 4.1 代价一：写放大

- 写入 1 条数据 → 写入 `2^d` 行
- 2 维: 4 倍；3 维: 8 倍；5 维: 32 倍
- 如果你的业务**写入吞吐量极高**（每秒数千条写入），写放大会成为瓶颈

### 4.2 代价二：存储膨胀

- 最坏情况下的存储 = `∏(leaf_max_i + 1) × 日期数` 行
- 以 5 维为例：app(4)、endpoint(6)、statusCode(4)、env(3)、region(4)，共 `4×6×4×3×4 × 365` = **420,480 行/年**
- 对比普通表存储 100 万条明细 = 100 万行，差异不大——关键取决于唯一坐标组合数

### 4.3 代价三：不支持"实时灵活聚合"

- Space 模型只有写入时确定的 2^d 种上卷组合可用
- 如果想按"小时"而不是"天"来聚合 → 需要增加维度或修改表结构
- 不适合"Ad-hoc 随意组合维度"的 BI 探索场景（那是 OLAP 数据库的专长）

### 4.4 什么时候选 Space 模型？

| 场景 | 推荐方案 |
|------|---------|
| 维度确定（≤10 个），取值范围有限（≤1000）| ✅ **Space 模型** |
| 需要毫秒级多维汇总 | ✅ **Space 模型** |
| 是小团队，不想引入 ClickHouse/Druid/Kylin 等重型平台 | ✅ **Space 模型** |
| 写入量不大（<1000 条/秒）| ✅ **Space 模型** |
| 需要灵活 Ad-hoc 任意维度组合 | ❌ OLAP 数据库（ClickHouse 等）|
| 写入吞吐量极高（万级/秒）| ❌ 时序数据库（InfluxDB 等）|
| 需要支持文本搜索 / LIKE 查询 | ❌ 搜索引擎（Elasticsearch 等）|

---

## 总结

| 问题 | Space 模型的答案 |
|------|-----------------|
| 为什么不是普通表？ | 普通表在查询时做聚合，数据越多越慢；Space 模型在写入时做聚合，数据再多查询都是 O(1) |
| 代价是什么？ | 写入放大 2^d 倍 + 存储膨胀；但只要维度数有限（≤10），代价是可控的 |
| 适合谁？ | 中小团队，维度确定的业务分析场景，不想引入 OLAP 复杂平台 |

**一句话**：Space 模型是一个**为小规模多维分析场景极致优化查询体验**的轻量方案。它用"写入时多做一些计算"换来了"查询时永远 1 行返回"的确定性性能。

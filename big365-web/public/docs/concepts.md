# 概念模型

本文档解释 big365 的核心设计理念与概念模型。理解这些概念能帮助你更好地使用 big365 进行多维数据管理。

## 核心理念：计算前置、零聚合查询

big365 的设计核心思想是 **"计算前置"**：

> 写入时多做一些计算，查询时就可以零聚合直接返回结果。

传统 OLAP 系统的工作方式是"查出明细 → 聚合计算 → 返回结果"，查询时计算量大。big365 采用相反的思路：写入每条数据时，把该数据对所有可能查询组合的贡献提前计算并写入，查询时只需定位到对应行直接读取即可。

---

## Dimension（维度）

**维度** 是业务分析的元数据定义，描述你关心的分析角度。

例如，在"日志监控"业务中，你可能有这些维度：

| 列名 | 显示名 | 取值范围 | 说明 |
|---|---|---|---|
| `a` | app（应用） | 1~10 | 哪个应用产生的日志 |
| `b` | endpoint（接口） | 1~100 | 哪个接口的日志 |
| `c` | status_code（状态码） | 1~500 | HTTP 状态码 |

每个业务拥有自己独立的维度表，维度之间互不影响。

---

## Coordinate（坐标）

**坐标** 是一个维度的具体取值。

例如，`a=3` 表示"应用编号为 3"，`b=7` 表示"接口编号为 7"。

---

## Vector（向量）

**向量** 是多个坐标组成的完整数据记录，包含各维度的取值 + 日期 + 指标值。

例如：

```
坐标: {a=3, b=7, c=200}
日期: 20260101
指标: 500（当日该组合的请求量）
```

---

## 0=ALL 哨兵

**0=ALL 哨兵** 是 big365 实现"零聚合查询"的核心机制。

规则很简单：

| 坐标值 | 含义 |
|---|---|
| `0` | **ALL** — 代表该维度的全部取值，即"上卷" |
| `1, 2, 3, ...` | 具体的叶子取值 |

举例：当有 3 个维度 a、b、c 时：

- `a=0, b=0, c=0` → **Grand Total（全局总计）**
- `a=3, b=0, c=0` → a=3 在所有 b 和 c 上的**聚合**
- `a=3, b=7, c=0` → a=3, b=7 在所有 c 上的**聚合**
- `a=3, b=7, c=200` → **叶子级**精确值

---

## 级联更新

这是 big365 最核心的写入算法。写入一条数据时，系统自动生成该数据在所有聚合级别的贡献行。

### 示例

假设业务注册了 **2 个维度**（d=2），维度 A 取值 1~10，维度 B 取值 1~100。

用户写入数据：

```
坐标: {a=3, b=7}
日期: 20260101
指标: 100
```

系统自动生成 **`2^2 = 4` 行**，涵盖所有上卷组合：

```
┌─────┬─────┬──────────┐
│  a  │  b  │ 20260101 │
├─────┼─────┼──────────┤
│ 3   │ 7   │ 100      │  ← 叶子级: a=3, b=7
│ 3   │ 0   │ 100      │  ← a=3 在所有 b 上的聚合
│ 0   │ 7   │ 100      │  ← b=7 在所有 a 上的聚合
│ 0   │ 0   │ 100      │  ← Grand Total（全局总计）
└─────┴─────┴──────────┘
```

每行的指标值 `100` 都表示在写入的那一刻，"这个坐标组合"的总指标为 100。

如果后续再次写入同一坐标+日期的数据（`a=3, b=7, date=20260101, value=50`），系统会在原有 4 行的基础上**累加**（`INSERT ... ON DUPLICATE KEY UPDATE`），4 行都会同时更新。

级联更新的行数 = `2^维度数`。例如：
- 2 维 → 4 行
- 3 维 → 8 行
- 5 维 → 32 行

---

## 零聚合查询

因为有 0=ALL 哨兵和级联更新，查询变得极其简单：

> 查询 = 构造坐标条件 → 定位到唯一一行 → 读取指标列

### 查询示例

沿用上文 2 维示例（a∈[1,10]，b∈[1,100]），查询 20260101 的数据：

```bash
# Grand Total（全局总计）
curl "http://localhost:18080/api/log_monitor/space/query?a=0&b=0&date=20260101"
# 返回: value=100
# 内部: SELECT `20260101` FROM space_t WHERE a=0 AND b=0  → 1 行

# 下钻: 只看 a=3 的所有数据
curl "http://localhost:18080/api/log_monitor/space/query?a=3&b=0&date=20260101"
# 返回: value=100
# 内部: SELECT `20260101` FROM space_t WHERE a=3 AND b=0  → 1 行

# 叶子级: 精确到 a=3, b=7
curl "http://localhost:18080/api/log_monitor/space/query?a=3&b=7&date=20260101"
# 返回: value=100
# 内部: SELECT `20260101` FROM space_t WHERE a=3 AND b=7  → 1 行
```

每次查询只扫描 **1 行**，时间复杂度 **O(1)**，无论数据量多大。

## 多业务隔离

big365 支持同时管理多个独立的业务。每个业务拥有完全独立的存储表：

```
big365_swks_log_monitor_dimensions_t    # 日志监控的维度定义
big365_swks_log_monitor_space_t         # 日志监控的数据空间
big365_swks_log_monitor_demo_jobs_t     # 日志监控的演示任务

big365_swks_sales_dimensions_t          # 销售分析的维度定义
big365_swks_sales_space_t               # 销售分析的数据空间
big365_swks_sales_demo_jobs_t           # 销售分析的演示任务
```

不同业务的维度数、维度类型、日期范围可以完全不同，互不干扰。

## 总结

| 特性 | 说明 |
|---|---|
| **计算前置** | 写入时完成所有聚合计算 |
| **0=ALL 哨兵** | 用 0 代表 ALL，实现上卷查询 |
| **级联更新** | 1 条写入 → `2^d` 行更新 |
| **零聚合查询** | 查询 = 定位 1 行 + 读取值，O(1) 时间复杂度 |
| **多业务隔离** | 每业务独立坐标表 + 独立维度表 |

### 空间复杂度

`总行数 = ∏(leaf_max_i + 1)`（每维取值范围含 ALL）。

例如：a∈[1,10] (11 个值含 ALL)，b∈[1,100] (101 个值含 ALL)，空间为 `11 × 101 × 日期数` 行。

设计上已假设维度取值范围有限（通常 `leaf_max ≤ 1000`），确保不会出现组合爆炸。

# ADR-002: MySQL 普通表采用预计算物化立方体模型

## 状态
ACCEPTED

## 背景

big365 MVP 需要使用 MySQL 普通表作为首个存储实现。原始 `bigdata_365` 已证明：可以在 MySQL 普通表上实现预计算物化立方体——坐标列（0=ALL 哨兵）+ 日期宽列 + 写入时级联更新。

因此需要决定 MVP 是沿用这套核心模型（去掉分区表），还是退化为行式 JSON 记录模型。

候选方案：

1. 预计算立方体：沿用原始 0=ALL + 级联更新 + 日期宽列，仅去掉分区表。
2. 行式 JSON 模型：每行一个时间点记录，查询时通过 GROUP BY 聚合。

## 决策

**采用预计算物化立方体模型**，直接继承原始设计的核心机制：

- 坐标列为 `a, b, c, d, e`（5 维），每列取值 `0=ALL | 1..max=叶子值`。
- 主键 `(a, b, c, d, e)`，索引 `idx_pid(pid)`。
- 日期列横向展开（如 `20260101`, `20260102`），每列是一个 `int unsigned` 指标值。
- 写入时级联更新 2^d 行，计算全部前置。
- 查询时按坐标定位读一行，零 `SUM`、零 `GROUP BY`。

仅分区表暂不引入。

## 后果

正面影响：

- 完整继承原始设计的核心价值：计算前置、零聚合查询。
- 保留了多维下钻、上卷、切片的天然能力。
- 查询复杂度 O(1)，与数据量无关。
- 与原始设计思想一致，后续演进路径清晰。

负面影响：

- 写入放大：每条数据 = 2^5 = 32 行更新。
- 日期扩展需要 DDL：新增日期 = ALTER TABLE 加列。
- 维度变更需要重建表。

缓解措施：

- MVP 数据规模小（~374 万行），32 倍写入仍在可接受范围。
- 首版只配置有限日期列，后续按需扩展。
- 维度变更频率低，首版维度确定后不会频繁调整。
